Chapter 3

Your First Test

Install Vibium, navigate to the app, read the page, write your first assertion, and run a complete working test — all against automation-exercise.daisyladybug.com.

Hands-on TypeScript ~20 min
Prerequisites

What You Need First

Before installing anything, make sure your machine has:

  • Node.js 18 or later. Run node --version to check. If it's not installed, go to nodejs.org and download the LTS release.
  • npm ships bundled with Node.js — if Node is installed, npm is already there.
  • A code editor. VS Code works well for TypeScript — autocomplete and inline type errors out of the box.

That's all. Vibium manages its own browser binaries internally, so you don't need to install Chrome separately.

3.1

Installing Vibium

Create a new directory for your project and install the Vibium TypeScript client and tsx, which lets you run TypeScript files directly without a separate compile step.

$ mkdir my-vibium-tests && cd my-vibium-tests
$ npm init -y
$ npm install vibium
$ npm install --save-dev tsx typescript

Create a tsconfig.json:

tsconfig.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "skipLibCheck": true,
    "esModuleInterop": true
  }
}

That's the complete setup. Vibium manages its own browser binaries — no additional prerequisites.

3.2

Your First Navigation

Let's make sure everything works. Create a file at src/ch03-first-test/01-navigate-and-read.ts and run it with npx tsx. A browser window will open, navigate to the app, and close. That's all this does — but it confirms your setup is working.

ch03/navigate.ts
import { browser as vibium } from 'vibium'

const AUT = 'https://automation-exercise.daisyladybug.com/'

async function main() {
  const browser = await vibium.start({ headless: false })
  const context = await browser.newContext()
  const page    = await context.newPage()

  await page.go(AUT)

  console.log('navigated successfully')
  await browser.stop()
}

main()

The key option to notice is headless: false. During development and learning, always keep this — you want to see what the browser is doing. Once your tests are solid, switch to headless: true for CI speed, which we'll cover in Chapter 9.

What's happening behind the scenes: When vibium.start() is called, Vibium quietly starts a background daemon process — a lightweight service that manages Chrome on the client's behalf. Your TypeScript code sends commands to the daemon; the daemon talks to Chrome. Locally this is automatic and invisible. You'll need to manage the daemon lifecycle explicitly when running in CI, and Chapter 9 covers exactly how. For now, it just works.

3.3

Reading the Page

Navigating is a start, but tests need to read the page to know what's there. page.title() returns the document title — the text you see in the browser tab. page.find() locates an element and gives you an object you can inspect and interact with. We're using { role, text } rather than CSS selectors here — role-plus-text locators stay stable when the page's structure changes.

ch03/01-navigate-and-read.ts
await page.go(AUT)

const title = await page.title()
console.log(title)
// "automation-exercise | E-commerce Testing Sandbox"

const heading = await page.find({ role: 'heading', text: 'automation-exercise' })
console.log(await heading.text())
// "automation-exercise"

const featured = await page.find({ role: 'heading', text: 'Featured Products' })
console.log(await featured.text())
// "Featured Products"
3.4

Your First Assertion

Reading the page is useful for debugging. But the whole point of a test is to verify that what you see matches what you expect. Node.js ships with a built-in assert module — no testing framework needed yet. The /strict import means all comparisons use strict equality and failed assertions throw with helpful messages. Always provide a label as the third argument — it appears in the error output and tells you exactly which assertion failed.

ch03/02-first-assertion.ts
import assert from 'node:assert/strict'

// assert.equal — checks two values are identical
const title = await page.title()
assert.equal(title, 'automation-exercise | E-commerce Testing Sandbox')
console.log('✓ page title correct')

// assert.ok — checks a value is truthy
const heading = await page.find({ role: 'heading', text: 'automation-exercise' })
assert.ok(await heading.isVisible())
console.log('✓ hero heading visible')
3.5

A Complete Test

Now let's put everything together. Three habits to establish right from the start: use try/finally so the browser always closes even on failure, call process.exit(1) on error so CI knows the test failed, and label every assertion. Here's the complete test with five assertions — each one checking something different about the homepage:

ch03/03-complete-test.ts
import { browser as vibium } from 'vibium'
import assert from 'node:assert/strict'

const AUT = 'https://automation-exercise.daisyladybug.com/'

async function testHomepage() {
  const browser = await vibium.start({ headless: false })
  const context = await browser.newContext()
  const page    = await context.newPage()

  try {
    await page.go(AUT)

    assert.equal(
      await page.title(),
      'automation-exercise | E-commerce Testing Sandbox',
      'page title'
    )

    const hero = await page.find({ role: 'heading', text: 'automation-exercise' })
    assert.ok(await hero.isVisible(), 'hero heading visible')

    const featured = await page.find({ role: 'heading', text: 'Featured Products' })
    assert.ok(await featured.isVisible(), 'Featured Products section visible')

    const product = await page.find({ text: 'Wireless Headphones Pro' })
    assert.ok(await product.isVisible(), 'first featured product visible')

    const cta = await page.find({ role: 'link', text: 'Explore Products' })
    assert.ok(await cta.isVisible(), 'Explore Products CTA visible')

    console.log('All assertions passed.')
  } finally {
    await browser.stop()
  }
}

testHomepage().catch(err => {
  console.error('Test failed:', err.message)
  process.exit(1)
})

What each assertion is checking:

1
Page title — smoke test; catches total navigation failure immediately.
2
Hero heading visible — checks rendered state, not just DOM presence.
3
Featured Products heading visible — confirms the page rendered past the hero.
4
Wireless Headphones Pro visible — confirms product data loaded.
5
Explore Products CTA visible — confirms the primary call-to-action is present.
3.6

Running It

Add a script to package.json and run it:

$ npm run ch03:complete
All assertions passed.

Now I want you to see what a failure looks like, because reading test failures is a skill. Temporarily change the expected title to something wrong. The output will show you exactly what went wrong:

Test failed: Expected values to be strictly equal:
+ actual - expected

+ 'automation-exercise | E-commerce Testing Sandbox'
- 'wrong title'

The + line is what you got. The - line is what you expected. The assertion label tells you which check failed. Revert the change, confirm it passes cleanly, and move on.

3.7 — Bonus

Recording Your Test for Review

There's one more tool worth introducing: Vibium's built-in test recorder. When you wrap your test in vibium.record() instead of vibium.start(), it captures every browser action, DOM state, and network event as the test runs.

recording a test run
const { browser, stop } = await vibium.record({ headless: false })
// ... your test logic ...
await browser.stop()
const url = await stop()
console.log('Recording:', url)
// → https://player.vibium.dev/session/abc123

stop() returns a URL at player.vibium.dev. Open it in any browser and you get an interactive replay — scrub forward and backward through every step, inspect the DOM at each point, and see which network requests fired. Think of it as a time machine for your test run.

This is similar in spirit to Playwright's trace recorder, but built directly into the API. The most valuable use case is debugging CI failures: when a test passes locally but fails in CI, add vibium.record() to the CI run, get the URL from the logs, and replay exactly what happened. We'll revisit this in Chapter 9.
