Chapter 8

Network Interception

Break the dependency on external APIs. Intercept HTTP requests before they leave the browser and return synthetic responses — deterministic, fast, and isolated.

Intermediate TypeScript ~20 min
8.1

page.route() — Two Methods

Any test that calls a real API inherits the instability of that API — slow responses, rate limits, flaky connections, data you can't predict. page.route(pattern, handler) breaks that dependency. You register an intercept before navigating — the pattern is a glob string matched against the full request URL, and the handler receives a Route object. Once registered, every matching request goes through your handler instead of hitting the network:

route.fulfill(response)
Respond with synthetic data: status, contentType, body.
route.abort()
Simulate a network failure — connection refused.
route.continue()
Pass the request through to the real server unchanged.
route.request().url()
Read the request URL to decide how to handle it.
8.2

Stubbing a Successful Response

Let's stub the products endpoint to return exactly two items, then verify the UI renders them. The test is fast — no real HTTP request leaves the browser. It always returns the same data, so assertions are deterministic. And it passes even when the real server is down.

fastNo real network call — milliseconds, not seconds
stableYour stub can't return rate-limit errors or unexpected data
isolatedPasses in CI even when the real API is down for maintenance
ch08/01-stub-response.ts (excerpt)
await page.route('**/api/products*', async route => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify([
      { id: 'prod_001', name: 'Wireless Headphones', price: 79.99 },
      { id: 'prod_007', name: 'Coffee Maker', price: 49.99 },
    ]),
  })
})

await page.go(`${AUT}/products`)
const count = await page.count('a[href*="/products/prod_"]')
assert.equal(count, 2, 'stubbed response shows 2 products')
8.3 – 8.5

Errors, Status Codes, and Partial Intercepts

Use route.abort() to simulate a connection-level failure — what happens when a request times out or DNS fails. Use status: 500 in fulfill() for a more realistic server error — the network worked, but the server responded with failure. Both scenarios are real; both are worth testing. The distinction matters: a 500 tests error handling over a working connection; an abort tests what happens when the connection itself is lost.

abort + partial intercept patterns
// simulate connection failure
await page.route('**/api/products*', async route => {
  await route.abort()
})

// let everything else through, stub only one endpoint
await page.route('**/*', async route => {
  if (route.request().url().includes('/api/products')) {
    await route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify([]),
    })
  } else {
    await route.continue()
  }
})

Partial intercepts are useful when you need to stub one API while the rest of the app (scripts, fonts, images, other APIs) loads normally from the real server.
