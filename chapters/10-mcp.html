10.1

Three Interfaces

Every chapter until now has been about writing code that drives the browser. You write the steps, define the selectors, control every action. In this final chapter we look at something fundamentally different: the Model Context Protocol, where you describe what you want in natural language and an AI agent figures out the steps. This isn't replacing what you've learned — it's extending it. The TypeScript client and MCP are two tools in the same toolkit.

Vibium ships with three interfaces, all talking to the same daemon. Each has a different driver and a different purpose:

Interface Who drives it Best for
CLI You, at a terminal Exploration, one-off checks
TypeScript client You, in code Deterministic test suites
MCP server An AI agent Open-ended exploration, test generation
10.2 – 10.3

What MCP Is and How to Start It

The Model Context Protocol is an open standard — similar in purpose to what USB is for hardware. When Vibium runs as an MCP server, it exposes its browser automation capabilities — navigate, find, click, fill, screenshot — as MCP tool calls. Any AI model that speaks MCP can invoke those tools. From your perspective: describe what you want to test, and the agent navigates a real browser, reads the page, takes actions, and reports back.

You need Claude Desktop installed on your machine to follow this section — download it from claude.ai and create a free account if you don't have one. The MCP integration runs entirely locally; Claude Desktop spawns the Vibium MCP server as a subprocess and connects to it, no cloud relay involved.

Once Claude Desktop is installed, open its config file and add the Vibium server entry. The file location depends on your OS: ~/Library/Application Support/Claude/claude_desktop_config.json on macOS, or %APPDATA%\Claude\claude_desktop_config.json on Windows.

claude_desktop_config.json
{
  "mcpServers": {
    "vibium": {
      "command": "vibium",
      "args": ["mcp"]
    }
  }
}

Restart Claude Desktop. You'll see Vibium tools become available — look for the hammer icon in the interface, which indicates active MCP connections. Claude Desktop starts the Vibium daemon automatically when it launches vibium mcp, so you don't need to run vibium daemon start separately here. From here, you can interact with a live browser through natural language.

10.4

Side-by-Side Comparison

The same scenario expressed two ways:

TypeScript client — deterministic
await page.go(`${AUT}/products`)
const select = await page.find('select:first-of-type')
await select.selectOption('Electronics')
await page.find({ text: 'Showing 3 of 12 products' })
const count = (await page.findAll('a[href*="/products/prod_"]')).length
assert.equal(count, 3)
MCP prompt — agent-driven
Go to automation-exercise.daisyladybug.com/products. Filter by the Electronics category. Tell me how many products are shown and what their names are.

The TypeScript version knows the selector, knows the expected count, and will fail with a clear message if either changes. The MCP version doesn't need to know any of that — Claude finds the dropdown, identifies the correct option, applies the filter, reads the results, and tells you what it found. Neither is better; they're different tools for different moments.

10.5

When to Use Each

TypeScript client
  • Writing a regression test
  • Need deterministic pass/fail
  • Running unattended in CI
  • Cost matters (no LLM calls)
MCP / agent-driven
  • Exploring an unfamiliar page
  • Generating test cases from scenarios
  • Debugging a flaky test
  • Prototyping before writing tests

The generation workflow: Use MCP to explore a flow — describe the scenario in natural language, watch the agent navigate and discover selectors. Then ask it to generate the TypeScript test. Review it, clean it up, add it to your suite. Agents for exploration and generation; TypeScript for the final executable tests. This workflow is especially powerful for large apps with many pages.

Exercise

MCP-Assisted Checkout Test

Use Claude Desktop (with Vibium MCP configured) to generate a test for the checkout page:

  1. Ask Claude: "Navigate to automation-exercise.daisyladybug.com/products, add any product to the cart, then explore the checkout page. List every form field by name, and check whether a validation error appears for each field when you submit the form empty."
  2. Let the agent explore the page and report back
  3. Take the agent's output and write a TypeScript test called testCheckoutValidationMCP that adds a product, navigates to /checkout, clicks "Place Order" without filling anything, and asserts at least 5 of the validation error messages the agent found are visible
  4. Run the test with npx tsx and confirm it passes

Reflect: which parts did the agent get right, and which parts needed correction before the test would run?
