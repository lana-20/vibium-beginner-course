Chapter 9

Running in CI

Tests that only run on your laptop aren't tests — they're demos. Configure headless mode, browser sharing, environment variables, a pre-baked Docker CI image, and a complete GitHub Actions workflow.

DevOps GitHub Actions Docker ~25 min
9.1

headless: true in CI

A test suite that only runs on your laptop is not a test suite — it's a demo. The whole point of automated testing is that the machine runs the checks every time someone pushes code. CI runners don't have a display server, so headless: false will fail immediately. The solution: read from process.env.CI. GitHub Actions sets it automatically for every job. Locally it's unset, so the browser opens visibly. In CI, it's 'true' and the browser runs headlessly.

env-aware headless mode
// headless: false locally, true in CI
const headless = process.env.CI === 'true'
const browser = await vibium.start({ headless })
9.2 – 9.3

Exit Codes and the Daemon

CI systems determine whether a job passed or failed by the process exit code. If your test fails but the process exits with 0, CI thinks everything is fine. Vitest handles exit codes automatically. For standalone scripts, the .catch(err => { process.exit(1) }) pattern from earlier chapters is why it's there.

Vibium's architecture separates the client from the browser. The TypeScript code you write doesn't talk to Chrome directly — it sends messages to a background daemon process, which manages the browser on its behalf. Locally, this is invisible: the first time you call vibium.start(), the client checks whether a daemon is running and starts one automatically if not. You never think about it. CI breaks this assumption — each workflow job starts from a clean environment with no persistent processes, so nothing auto-starts. You manage the daemon lifecycle explicitly: start it before your tests, stop it after.

daemon lifecycle in workflow
- name: Start Vibium daemon
  run: vibium daemon start

- name: Run tests
  run: npm test

- name: Stop Vibium daemon
  if: always()         # runs even if tests fail
  run: vibium daemon stop
9.3b — Browser Sharing

One Browser, Many Tests

Starting a fresh browser for every test is simple but slow — each start and stop costs a few seconds. Share one browser across all tests in a suite using beforeAll/afterAll, and open a fresh context per test with beforeEach/afterEach. This is the same pattern Playwright uses for multiple tabs: one browser, isolated contexts.

shared browser, isolated contexts
describe('Products page', () => {
  let browser: Awaited<ReturnType<typeof vibium.start>>
  let context: any
  let page: any

  beforeAll(async () => {
    browser = await vibium.start({ headless: process.env.CI === 'true' })
  })
  afterAll(async () => { await browser.stop() })

  beforeEach(async () => {
    context = await browser.newContext()  // fresh cookies, storage
    page = await context.newPage()
  })
  afterEach(async () => { await context.close() })

  it('shows 12 products', async () => { /* ... */ })
  it('filters by category', async () => { /* ... */ })
})

beforeAll starts one browser for the whole block. Each test gets a fresh newContext() — cookies, localStorage, and navigation history are fully isolated. afterEach closes the context so state never bleeds between tests. afterAll stops the browser once every test in the suite has finished.

9.4

The GitHub Actions Workflow

The container key tells GitHub Actions to run every step inside a pre-built Docker image. That image — ghcr.io/lana-20/vibium-ci:latest — already has Chrome downloaded and patched. HOME: /root appears on every Vibium step because the image was built as root: Chrome lives at /root/.cache/vibium and the Node.js API needs to know where to look.

.github/workflows/tests.yml
name: Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:         # manual trigger from the Actions tab

jobs:
  test:
    runs-on: ubuntu-latest
    container: ghcr.io/lana-20/vibium-ci:latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - name: Install dependencies
        run: npm ci
      - name: Start Vibium daemon
        run: vibium daemon start
        env:
          HOME: /root
      - name: Run tests
        run: npm run test:ci
        env:
          CI: true
          HOME: /root
          AUT_BASE_URL: ${{ vars.AUT_BASE_URL }}
      - name: Stop Vibium daemon
        if: always()
        run: vibium daemon stop
        env:
          HOME: /root
9.5

Environment Variables

Hard-coding URLs in test code creates a problem: running tests against a staging environment or a preview deployment requires code changes. Use environment variables instead — but use ||, not ??.

env-aware AUT URL
const AUT = process.env.AUT_BASE_URL
  || 'https://automation-exercise.daisyladybug.com'

Why || and not ??: GitHub Actions vars.* returns an empty string "" when a variable is not configured. The ?? operator only falls back for null and undefined — it passes "" through, leaving you with an empty URL and a confusing failure. || catches any falsy value, so the fallback always works whether the variable is unset or blank.

Secrets vs vars: Use secrets.* for API keys and passwords — never vars.*. GitHub masks secrets in logs; vars are visible.

Local .env file: Add a .env file to your gitignore and use a package like dotenv to load it locally. Never commit .env files.

9.6 — Observability

Debugging CI Failures with Recordings

There's a class of failure that's very frustrating: the test passes locally every time but fails in CI. This is where vibium.record() becomes essential. Add it to your CI test run — stop() returns a URL at player.vibium.dev that appears in your workflow logs.

adding a recording to a CI test
const { browser, stop } = await vibium.record({
  headless: process.env.CI === 'true',
})
// ... test logic ...
await browser.stop()
const url = await stop()
console.log('Recording:', url)
// → https://player.vibium.dev/session/abc123

Click the URL and you get an interactive replay — scrub forward and backward through every step, inspect the DOM at each point, and see which network requests fired. You can identify exactly where things went wrong: was an element present but not visible? Did a waitForText time out because a request was slow? The recording tells you. No more guessing from stack traces.

9.7 — Docker

Pre-Baking a CI Image

The default approach downloads Chrome on every run — about 300 MB, which costs 20–30 seconds. The better approach: bake Chrome into a Docker image, push it once to a registry, and pull it on every run. Chrome is always there. No download, no wait.

Dockerfile.ci
FROM node:20-slim

RUN apt-get update && apt-get install -y --no-install-recommends \
    libatk1.0-0 libatk-bridge2.0-0 libcups2 libdrm2 \
    libxkbcommon0 libxcomposite1 libxdamage1 libxfixes3 \
    libxrandr2 libgbm1 libasound2 libnspr4 libnss3 \
    libcairo2 libpango-1.0-0 libpangocairo-1.0-0 \
    libx11-6 libx11-xcb1 libxcb1 libxcursor1 libxext6 \
    libxi6 libxrender1 libxtst6 libdbus-1-3 \
    fonts-liberation ca-certificates \
    && rm -rf /var/lib/apt/lists/*

RUN npm install -g vibium && vibium install

RUN CHROME=$(find /root/.cache/vibium -name "chrome" -not -name "chromedriver" | head -1) \
    && mv "$CHROME" "${CHROME}.real" \
    && printf '#!/bin/sh\nexec "%s.real" --no-sandbox --disable-dev-shm-usage "$@"\n' "$CHROME" > "$CHROME" \
    && chmod +x "$CHROME"

ENV HOME=/root

The long apt-get install list is the exact set of system libraries Chrome for Testing needs on Debian Bookworm. The non-obvious one is libcairo2 — Chrome uses Cairo for 2D rendering even in headless mode. If it's missing, Chrome exits immediately with exit code 1 and no output. Silent failures like this are only diagnosed by running Chrome directly with output captured.

The wrapper script solves two Linux container constraints. AppArmor on Ubuntu CI runners blocks Chrome's process sandbox — --no-sandbox bypasses it. Docker's /dev/shm is limited to 64 MB; Chrome exhausts it rendering pages — --disable-dev-shm-usage redirects to /tmp. The wrapper renames the real binary to chrome.real and replaces it with a shell script that injects both flags transparently.

ENV HOME=/root ensures Node.js finds Chrome at /root/.cache/vibium — where vibium install put it when the image was built as root.

Auto-rebuild: A second workflow (build-ci-image.yml) watches for changes to Dockerfile.ci and rebuilds the image automatically. Update the Dockerfile, push — the next test run picks up the new image.

9.8 — Demo

The Hands-On Demo: Push, Watch, Fail, Fix

Everything in this chapter becomes concrete once you push the repo to GitHub. The workflow file is already in .github/workflows/tests.yml — it triggers automatically on every push.

1
Push the repo. Open github.com/your-username/vibium-beginner-course → Actions tab → watch the run start.
2
Watch it pass. Each step gets a green checkmark in real time: checkout → setup → install → daemon → tests → daemon stop.
3
Break a test. Change one assertion to assert the wrong value. Push. Watch the Actions tab go red.
4
Find the recording URL in the failing step's log output. Open player.vibium.dev — scrub to the assertion failure.
5
Fix it, push again. Watch it go green. That's the full CI feedback loop.
