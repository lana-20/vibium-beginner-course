# Chapter 9: Running in CI

A test suite that only runs on your laptop is not a test suite — it's a demo. The entire point of automated testing is that the machine runs the checks every time someone pushes code, so bugs get caught before they reach production. In this chapter we're going to take everything we've built and make it run on GitHub Actions. That means configuring headless mode correctly, managing the Vibium daemon lifecycle, passing secrets through environment variables, and using recordings to debug failures that only appear in CI.

---

## headless: true in CI

CI runners don't have a display server. There's no screen, so there's no browser window to show. If you run with `headless: false`, the process fails immediately.

But you don't want to just hard-code `headless: true` either — during development, you want to see the browser. The solution is an environment variable:

```typescript
const headless = process.env.CI === 'true'
const browser = await vibium.start({ headless })
```

GitHub Actions sets `CI=true` automatically for every job. Locally, `CI` is unset, so this expression evaluates to `false` and the browser opens visibly. When your code runs in CI, `CI` is `'true'` and the browser runs headlessly. One change, both environments covered.

---

## Exit codes

CI systems determine whether a job passed or failed by the process exit code. Exit code 0 means success; anything non-zero means failure. If your test fails but the process exits with 0, CI thinks everything is fine.

This is why every standalone script in this course ends with:

```typescript
main().catch(err => {
  console.error('Test failed:', err.message)
  process.exit(1)
})
```

The `.catch` catches any thrown error, logs it, and forces exit code 1. Without this, a thrown error in an async function might print to stderr but not set a non-zero exit code — depending on the Node.js version and how the script is invoked.

When you use Vitest, this is handled automatically. A failing test causes `vitest run` to exit with code 1. You don't need to manage it manually in test files.

## The Vibium daemon in CI

Vibium's TypeScript client communicates with a local daemon process. That daemon must be running before your tests start. In CI, you need to start it explicitly in your workflow and stop it when you're done.

The key pattern:

```yaml
- name: Start Vibium daemon
  run: vibium daemon start

- name: Run tests
  run: npm test

- name: Stop Vibium daemon
  if: always()
  run: vibium daemon stop
```

The `if: always()` on the stop step is critical. Without it, if the test step fails, the stop step is skipped — and you leave a daemon process running in the CI environment. `if: always()` means this step runs regardless of whether previous steps succeeded or failed. It's the YAML equivalent of `finally` in TypeScript.

## One browser, many tests

Starting a fresh browser for every test is the simplest approach, and it's fine for small suites. But each browser start and stop costs a few seconds — in CI, where you have no need to isolate between test runs anyway, you can share one browser across all tests in a suite and only create a fresh context per test.

This is exactly how Playwright handles multiple tabs: one browser, isolated contexts.

```typescript
describe('Products page', () => {
  let browser: Awaited<ReturnType<typeof vibium.start>>
  let context: any
  let page: any

  beforeAll(async () => {
    browser = await vibium.start({ headless: process.env.CI === 'true' })
  })

  afterAll(async () => {
    await browser.stop()
  })

  beforeEach(async () => {
    context = await browser.newContext()
    page = await context.newPage()
  })

  afterEach(async () => {
    await context.close()
  })

  it('shows 12 products', async () => { /* ... */ })
  it('filters by category', async () => { /* ... */ })
})
```

`beforeAll` starts one browser for the whole describe block. `beforeEach` opens a fresh context and page for each test — cookies, localStorage, and navigation history are all isolated. `afterEach` closes the context so state doesn't bleed between tests. `afterAll` stops the browser once every test in the suite has finished.

If `beforeAll` throws (browser fails to start), every test in the block is marked as failed and `afterAll` still runs. The individual `afterEach` calls don't run for tests that never started — which is fine, since there's nothing to clean up.

## The complete GitHub Actions workflow

Here's the full workflow file in `.github/workflows/tests.yml`:

```yaml
name: Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:

jobs:
  test:
    runs-on: ubuntu-latest
    container: ghcr.io/lana-20/vibium-ci:latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Start Vibium daemon
        run: vibium daemon start
        env:
          HOME: /root

      - name: Run tests
        run: npm run test:ci
        env:
          CI: true
          HOME: /root
          AUT_BASE_URL: ${{ vars.AUT_BASE_URL }}

      - name: Stop Vibium daemon
        if: always()
        run: vibium daemon stop
        env:
          HOME: /root
```

The `container` key tells GitHub Actions to run every step inside a pre-built Docker image rather than directly on the runner. That image — `ghcr.io/lana-20/vibium-ci:latest` — already has Chrome downloaded and patched. When the job starts, Chrome is ready immediately; no download, no patch step.

`HOME: /root` appears on every step that touches Vibium. The CI image was built as root, so Chrome lives at `/root/.cache/vibium`. GitHub Actions containers run with a non-root user by default, so you have to tell the process where to look.

`workflow_dispatch` makes the workflow manually triggerable from the Actions tab — useful when you want to re-run without pushing a commit.

The `AUT_BASE_URL` variable comes from your repo's Settings > Secrets and variables > Actions > Variables tab.

## Environment variables

Hard-coding URLs in test code creates a problem: running tests against a different environment (staging, preview deployment, local dev server) requires code changes. Use environment variables instead:

```typescript
const AUT = process.env.AUT_BASE_URL ?? 'https://automation-exercise.daisyladybug.com'
```

The `??` operator means: use `AUT_BASE_URL` if it's set, otherwise fall back to the default URL. Locally you can export the variable in your shell, or put it in a `.env` file (add `.env` to `.gitignore`). In CI, it comes from GitHub Actions.

For sensitive values — API keys, passwords, tokens — always use `secrets.*` rather than `vars.*` in GitHub Actions:

```yaml
env:
  API_KEY: ${{ secrets.API_KEY }}
```

Secrets are encrypted at rest and masked in logs. Variables are unencrypted and visible in logs — fine for things like base URLs, wrong for credentials.

## Debugging CI failures with recordings

There's a class of failure that's very frustrating: the test passes locally every time but fails in CI. The most common causes are timing differences (CI runners are slower than your laptop), environment differences (different Node.js version, network latency, font rendering), or test isolation issues (tests that pass in isolation but interfere in sequence).

This is where `vibium.record()` becomes essential. Add recording to your CI test run:

```typescript
async function testCheckoutFlow() {
  const { browser, stop } = await vibium.record({
    headless: process.env.CI === 'true',
  })
  const context = await browser.newContext()
  const page = await context.newPage()

  try {
    // ... test logic
  } finally {
    await browser.close()
    const url = await stop()
    console.log('Recording:', url)
  }
}
```

When the test runs in CI, the URL to `player.vibium.dev` appears in your workflow logs. Click it and you get an interactive replay — scrub through every action, see the DOM state at each step, inspect network requests, and identify exactly where things went wrong.

This is far more useful than reading a stack trace from a failure line number. You see what the browser actually showed at the moment of failure. You can check whether an element was present but not visible, whether a wait timed out because a network request was slow, or whether the assertion was asserting the wrong thing entirely.

For production use, you'd conditionally enable recording only when a test fails:

```typescript
let recordingUrl: string | undefined

try {
  const { browser, stop } = await vibium.record({ headless: true })
  // ... run test
  const url = await stop()
  recordingUrl = url
} catch (err) {
  if (recordingUrl) {
    console.error('Test failed. Recording:', recordingUrl)
  }
  process.exit(1)
}
```

## Verbose CI output

One more thing for your `package.json`:

```json
"scripts": {
  "test": "vitest run",
  "test:ci": "vitest run --reporter=verbose"
}
```

The default Vitest reporter is compact — fine for local development. In CI, verbose output is more useful: it prints each test name, pass/fail status, and timing, which makes log scanning faster when you're looking for a specific failure.

Use `npm run test:ci` in your workflow's run step instead of `npm test`.

## Pre-baking a CI image with Docker

The standard GitHub Actions approach downloads Chrome on every run — that's around 300 MB each time, which costs 20–30 seconds. The better approach is to build a Docker image with Chrome already inside it, push it to a registry, and point your workflow at that image. Chrome is always there, ready immediately.

This is the `Dockerfile.ci` at the root of this project:

```dockerfile
FROM node:20-slim

RUN apt-get update && apt-get install -y --no-install-recommends \
    libatk1.0-0 libatk-bridge2.0-0 libcups2 libdrm2 \
    libxkbcommon0 libxcomposite1 libxdamage1 libxfixes3 \
    libxrandr2 libgbm1 libasound2 libnspr4 libnss3 \
    libcairo2 libpango-1.0-0 libpangocairo-1.0-0 \
    libx11-6 libx11-xcb1 libxcb1 libxcursor1 libxext6 \
    libxi6 libxrender1 libxtst6 libdbus-1-3 \
    fonts-liberation ca-certificates \
    && rm -rf /var/lib/apt/lists/*

RUN npm install -g vibium && vibium install

RUN CHROME=$(find /root/.cache/vibium -name "chrome" -not -name "chromedriver" | head -1) \
    && mv "$CHROME" "${CHROME}.real" \
    && printf '#!/bin/sh\nexec "%s.real" --no-sandbox --disable-dev-shm-usage "$@"\n' "$CHROME" > "$CHROME" \
    && chmod +x "$CHROME"

ENV HOME=/root
```

There are several things here worth understanding.

The long `apt-get install` list is the set of system libraries Chrome for Testing actually needs on Debian. Many are obvious — `libnspr4`, `libnss3` for networking, `libgbm1` for GPU buffer management. The non-obvious one is `libcairo2`. Chrome uses Cairo for 2D rendering even in headless mode. If it's missing, Chrome exits immediately with no output and no useful error message. It took a debug step to confirm.

`npm install -g vibium && vibium install` installs the CLI and downloads Chrome. The Chrome binary lands at `/root/.cache/vibium/chrome-for-testing/...`.

The three-line RUN block creates a wrapper script. Linux CI runners run Chrome under AppArmor, which blocks Chrome's sandbox. Docker containers restrict `/dev/shm` to 64 MB, which Chrome exhausts immediately when rendering pages. Both problems need flags:

- `--no-sandbox` bypasses Chrome's process sandbox, which AppArmor would otherwise block
- `--disable-dev-shm-usage` tells Chrome to use `/tmp` instead of the limited `/dev/shm`

The wrapper renames the real Chrome binary to `chrome.real`, then creates a shell script at the original path that injects both flags before passing everything else through. Vibium launches Chrome by path — it finds the wrapper, the wrapper finds the real binary.

`ENV HOME=/root` ensures that when Node.js calls `os.homedir()` inside the container, it returns `/root` — where the Chrome download actually lives.

A second workflow, `.github/workflows/build-ci-image.yml`, rebuilds and publishes the image automatically whenever `Dockerfile.ci` changes:

```yaml
name: Build CI image

on:
  push:
    branches: [main]
    paths:
      - Dockerfile.ci
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v5
        with:
          context: .
          file: Dockerfile.ci
          push: true
          tags: ghcr.io/${{ github.repository_owner }}/vibium-ci:latest
```

The image is published to the GitHub Container Registry at `ghcr.io/lana-20/vibium-ci:latest`. The test workflow pulls it on every run. Update the Dockerfile, push — the image is rebuilt and the next test run picks it up automatically.

## The hands-on demo: pushing and watching it run

Everything in this chapter is visible and verifiable. Here's the complete demo sequence:

**Step 1 — push the repo to GitHub.** The workflow file is already in `.github/workflows/tests.yml`. Once the repo is on GitHub, every push triggers it automatically.

**Step 2 — navigate to the Actions tab.** Open your repo on github.com, click Actions. You'll see the workflow run start within seconds of your push.

**Step 3 — watch the run.** Click into the run. You'll see each step execute in real time: checkout, setup-node, install, daemon start, tests, daemon stop. Green checkmarks as each step passes.

**Step 4 — introduce a deliberate failure.** Change one assertion to something wrong — assert the page title equals `"wrong title"`. Push. Watch the Actions tab go red. Click into the failing step and find the recording URL in the logs.

**Step 5 — replay the failure.** Open the `player.vibium.dev` URL. Scrub to the failing assertion. The DOM panel shows exactly what was on screen at that moment.

**Step 6 — fix it.** Revert the change, push again. Watch it go green.

That five-step sequence — push, watch, fail, record, fix — is the core CI feedback loop. Everything else in this chapter is configuration that supports it.
