2.1

The Engine and the Interfaces

In Chapter 1 we talked about what Vibium is. In this chapter I want to show you how it works. We're going to look at the object hierarchy that everything in this course builds on, walk through a live browser session from start to finish, and touch on the three categories of things you can do with a Vibium page. Understanding this architecture will make every chapter that follows much easier to reason about.

Let me start by making the three-interface story concrete. When you install Vibium, you get access to the same browser engine through three different surfaces:

CLI
Standalone binary. One command at a time from the terminal. Great for exploration.
MCP Server
Implements the Model Context Protocol. AI agents drive the browser without any glue code.
Client Libraries
TypeScript, Python, Java. Full programmatic API. This is how tests are written.
↑ all three talk to the same underlying engine ↑

All three interfaces talk to the same underlying browser engine and share the same behavior. What you learn about finding elements, filling forms, and waiting for page changes applies equally across all three.

2.2

How a Test Actually Runs

Every interaction with Vibium follows the same four-level hierarchy. Browser is the top-level object — think of it as the application itself before any tabs are open. BrowserContext is an isolated session with its own cookies, storage, and authentication state. This is important for tests: two contexts can't share state, like two users in separate incognito windows. Page represents a single tab. Element is what you get back from page.find() — a specific DOM node you can interact with.

Notice every step is an await. Each call returns a promise you resolve before moving to the next level. Once you hold a page, most things you do are await page.something(). Once you hold an element, it's await element.something().

2.3

The Object Hierarchy

Vibium organizes browser automation around four levels:

1 Browser The browser process. One per test run. Start it, use it, close it.
2 BrowserContext Isolated session — own cookies, storage, auth state. Contexts run in parallel without interfering.
3 Page A single browser tab. Most tests work with one page at a time.
4 Element A DOM node: button, input, heading, link. Click it, read it, fill it.
ch02/browser-hierarchy.ts
import vibium from 'vibium'

const browser = await vibium.start({ headless: false })
const context = await browser.newContext()
const page    = await context.newPage()

await page.go('https://automation-exercise.daisyladybug.com/')

const button = await page.find({ role: 'link', text: 'Explore Products' })
await button.click()

await browser.stop()
2.4

Finding Elements

page.find() is the most important method in Vibium's API. It locates a single element and returns an object you can interact with. The key design decision is how you describe the element you want.

The role-plus-text approach describes what the element means, not what it looks like. "Button" refers to the semantic role — it doesn't matter whether the HTML is a <button>, an <a> styled as a button, or a <div role="button">. The text narrows it to the specific one. CSS selectors are a fallback for form inputs or elements where semantic targeting isn't precise enough.

find strategies
// role + text — most robust, use for interactive elements
const btn = await page.find({ role: 'button', text: 'Add to cart' })

// CSS selector — use when role+text isn't enough
const input = await page.find('#search-input')

// text only — fine for reading content, returns outermost match
const heading = await page.find({ text: 'Featured Products' })

Important: find({ text }) matches DOM text, not rendered text. CSS text-transform is never applied. If the DOM says "add to cart" but the page renders "ADD TO CART", search for "add to cart".

2.5

Actions, Captures, and Waits

Everything you do with a Vibium page falls into one of three categories. Understanding this mental model organizes every chapter from here on.

Actions are things you do to the page: navigate, click, fill, select. Captures are events the browser sends to you: dialogs, console messages, file downloads — set up the listener before triggering the action, always using Promise.all. Waits block your script until a condition is true: text appears, URL changes. The pattern you'll use constantly: trigger an action, wait for the DOM to settle, then assert.

captures — the key pattern
// Register the capture BEFORE triggering the action, always.
const [dialog] = await Promise.all([
  page.capture.dialog(),   // listener registered first
  button.click()            // action fires second
])

console.log(dialog.message)
await dialog.accept()
waits
await page._waitForURL('**/checkout/success')
await page.find({ text: 'Order confirmed' })
2.6

OOP: Why the Object Model Matters

You might notice that Vibium's API is object-oriented — you call methods on objects (page.find(), element.click()) rather than passing everything as arguments to standalone functions. This is intentional, and it matters for how you write good tests.

Each object in the hierarchy carries context. A Page knows which browser context it belongs to. An Element knows which page it came from and which DOM node it represents. When you call element.click(), Vibium doesn't re-query the DOM — it already has a reference to the exact node.

This OOP model is also the foundation for the Page Object Pattern in Chapter 6. When you wrap a page's interactions in a class, each method translates directly to one or more Vibium calls. The test doesn't know or care about selectors — it calls products.filterByCategory('Electronics'). That's OOP applied to test organization: changes in one place propagate everywhere automatically.

2.7

Atomic Tests

An atomic test does one thing and one thing only. It sets up its own state, performs its action, asserts the outcome, and tears down cleanly. It doesn't depend on another test having run before it. It doesn't leave side effects for the next test.

Why does this matter? Because if Test B depends on Test A having run first, and Test A fails, now both tests fail — but only one is actually broken. Debugging becomes harder. Tests become order-dependent, which means you can't run them in parallel. Over time the suite accumulates implicit dependencies that nobody can fully map.

In Vibium, atomicity means: every test gets its own browser context, navigates to its own starting URL, and closes the browser in finally. No shared state, no leftover cookies, no assumptions about what the previous test did. This is exactly what beforeEach and afterEach in Chapter 6 enforce structurally.

2.8

Network Layer

Vibium lets you intercept browser requests and fulfill them with mock responses, modify them, or block them. You won't need this in the early chapters — we'll work with the real app throughout. But it's worth knowing the feature exists for when tests become flaky because of an unstable external API.

network interception
await page.route('**/api/products', route => {
  route.fulfill({ status: 200, body: JSON.stringify({ products: [] }) })
})

Exercise

Walk the Full Hierarchy

Write a script called 02-explore.ts that walks the full Browser → Context → Page → Element hierarchy and logs something at each level:

  1. Create a browser with headless: false
  2. Create a context and a page
  3. Navigate to automation-exercise.daisyladybug.com
  4. Log the page title using page.title()
  5. Find the "Products" navigation link using { role: 'link', text: 'Products' } and log its href attribute
  6. Click the link and wait for page._waitForURL('**/products')
  7. Log the new URL with page.url()
  8. Find the first product link on the page and log its text
  9. Close the browser in finally

Expected terminal output: the homepage title, the Products href, the products URL, and one product name — all in sequence with no errors.
