Chapter 6

Organizing Tests

Move from standalone scripts to a Vitest suite. Share browser setup with beforeEach/afterEach, and wrap page interactions in Page Objects so selector changes land in one place.

Architecture Vitest ~25 min
6.1

From Scripts to a Suite

Every chapter so far has been standalone scripts — one file, one function, one async function main(). That's the right way to learn. But as your test suite grows, standalone scripts create real problems. Here's what breaks:

1Each file manages its own browser lifecycle — boilerplate in every file
2No built-in pass/fail reporting
3Running all tests means running each file manually
4No way to run only the tests for a specific feature

Vitest solves all four: it discovers test files automatically, runs them in parallel, reports results, and exposes describe/it/beforeEach/afterEach for structured suites. More importantly, it enforces structure that makes atomic tests easy to write correctly.

6.2

Setting Up Vitest

Install and configure Vitest, then add it to package.json:

vitest.config.ts
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    globals: false,
    testTimeout: 60_000,
    hookTimeout: 30_000,
    include: ['src/**/*.test.ts'],
  }
})

6.3

beforeEach and afterEach

Use lifecycle hooks to manage the browser. Each test gets a fresh browser context — tests can't share state accidentally. This is what atomic tests look like structurally: beforeEach creates a clean context, afterEach closes it regardless of whether the test passed or failed. If afterEach runs even when a test throws, you never leak browser processes.

browser lifecycle in a suite
describe('Products page', () => {
  let browser: Awaited<ReturnType<typeof vibium.start>>
  let page: any

  beforeEach(async () => {
    browser = await vibium.start({ headless: true })
    const context = await browser.newContext()
    page = await context.newPage()
  })

  afterEach(async () => {
    await browser.stop()
  })

  it('shows 12 products', async () => {
    await page.go(`${AUT}/products`)
    const count = (await page.findAll('a[href*="/products/prod_"]')).length
    expect(count).toBe(12)
  })
})
6.4

The Page Object Pattern

The Page Object Pattern is one of the most important ideas in professional test automation. It applies OOP directly to test organization: a class bundles related state and behavior together. The selectors for the products page belong together — they change together when the page changes. The actions on the products page belong together. The Page Object encapsulates this, exposing a clean interface. Tests call its methods. Tests never touch selectors directly.

This maps to the Single Responsibility Principle: the ProductsPage class has one job — representing the products page. Tests have one job — asserting on outcomes. A selector change in the products page means one edit in one file. Every test that uses filterByCategory() benefits automatically.

pages/ProductsPage.ts
export class ProductsPage {
  constructor(private page: any) {}

  async goto() {
    await this.page.go(`${AUT}/products`)
  }

  async search(query: string) {
    const input = await this.page.find("input[placeholder='Search products...']")
    await input.fill(query)
  }

  async filterByCategory(category: string) {
    const select = await this.page.find('select:first-of-type')
    await select.selectOption(category)
  }

  async productCount() {
    return (await this.page.findAll('a[href*="/products/prod_"]')).length
  }
}

The test using a Page Object becomes self-documenting:

test using ProductsPage
it('search finds a product by name', async () => {
  const products = new ProductsPage(page)
  await products.goto()
  await products.search('yoga')
  expect(await products.isProductVisible('Yoga Mat')).toBe(true)
  expect(await products.isProductVisible('Wireless Headphones')).toBe(false)
})

Rule of thumb: If a selector appears in more than two tests, it belongs in a Page Object. If it appears once, keep it inline.

6.4b — Running

What npm test Shows You

Run the suite with npm test. Vitest discovers every *.test.ts file in src/, runs them, and prints a result summary. A passing run looks like this:

terminal — all passing
 ✓ src/ch06-organizing/tests/products.test.ts (4 tests) 22s

 Test Files  1 passed (1)
      Tests  4 passed (4)
   Start at  14:32:11
   Duration  23.5s

If a test fails, Vitest names it and shows the assertion that failed:

terminal — one failure
 ✗ Products page > shows 12 products by default 6211ms
   → AssertionError: expected 11 to be 12

 Test Files  1 failed (1)
      Tests  1 failed | 3 passed (4)
   Duration  23.4s

The test name tells you exactly which case failed. The assertion message tells you what was expected. The other three tests still ran and passed — failures don't stop the suite.

6.5 — Bonus

Parallel Contexts — Multiple Tabs, One Browser

Playwright runs tests in parallel across multiple worker processes, each with their own browser instance. Vibium can achieve a similar result within a single browser process using multiple BrowserContext objects. Each context is fully isolated — its own cookies, storage, and auth state — and can run a Page independently.

Here's what that looks like — two users interacting with the app simultaneously, in the same browser process, without interfering with each other:

parallel contexts — two independent sessions
const browser = await vibium.start({ headless: true })

// two isolated contexts — like two incognito windows
const [ctx1, ctx2] = await Promise.all([
  browser.newContext(),
  browser.newContext(),
])

const [page1, page2] = await Promise.all([
  ctx1.newPage(),
  ctx2.newPage(),
])

// run both in parallel — they don't share any state
await Promise.all([
  page1.go(`${AUT}/products`),
  page2.go(`${AUT}/cart`),
])

await browser.stop()

Within a single Vitest suite, Vitest's parallel test runner handles this for you automatically — each test in the suite gets its own beforeEach-created context, and Vitest runs them concurrently. But if you need to orchestrate multiple browser sessions within a single test (for example, testing a real-time chat feature where two users must be active simultaneously), the multi-context pattern above is the right approach.
